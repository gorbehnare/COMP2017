11 - VPN Protocols

Source: https://learn.microsoft.com/en-us/windows-server/remote/remote-access/configure-vpn-protocols

Microsoft Windows Server and Windows client operating systems include built-in VPN support. These VPN protocols are commonly used because they are integrated into Windows and typically do not require additional client software installation.

When the Routing and Remote Access Service (RRAS) role is installed on Windows Server, it supports PPTP, L2TP/IPsec, SSTP, and IKEv2 VPN protocols. On Windows Server versions before Server 2025, RRAS accepts incoming VPN connections using any of these protocols by default.

Beginning with Windows Server 2025, new RRAS deployments accept SSTP and IKEv2 connections by default. PPTP and L2TP/IPsec remain available but must be explicitly enabled if required. Existing RRAS deployments that are upgraded to Windows Server 2025 retain their existing protocol configuration; for example, a server already accepting PPTP or L2TP/IPsec connections continues to do so after the upgrade.

Point-to-Point Tunnelling Protocol (PPTP) (Do NOT Use)

Refer to https://en.wikipedia.org/wiki/Point-to-Point_Tunneling_Protocol

  • PPTP uses a TCP control channel (port 1723) and encapsulates PPP frames inside a Generic routing encapsulation (GRE) tunnel.
  • PPTP solely relies on PPP to perform any authentication or encryption, and any other security functions
    • Several authentication methods are supported: PAP, CHAP, MS-CHAPv1, MS-CHAPv2, EAP
    • MS-CHAPv2 handles the authentication in most deployments
      • Bruce Schneier and Mudge published a cryptanalytic attack against PPTP/MS-CHAP in 1998 (see https://www.schneier.com/blog/archives/2012/08/breaking_micros.html), demonstrating significant weaknesses in the protocol suite.
      • Moxie Marlinspike (creator of the Signal protocol) demonstrated that MS-CHAPv2 could be reduced to the difficulty of cracking a single 56-bit DES key (trivial to crack on modern systems) in 2012. They have published a tool called chapcrack which uses external cracking resources to recover the corresponding authentication secret from a single captured authentication handshake.
  • PPTP (or rather, its encapsulated PPP link) can only use Microsoft Point-to-Point Encryption (MPPE), which is based on the broken RC4 with up to a 128-bit key (40-bit and 56-bit are also supported).
    • The RC4 stream cipher has no method for authentication of the ciphertext stream, and therefore the ciphertext is vulnerable to a bit-flipping attack (an attacker could modify the stream in transit and adjust single bits to change the output stream without possibility of detection).
    • MPPE does not provide modern authenticated encryption or strong cryptographic integrity protection.
  • Separate from its inherent cryptographic weaknesses, Windows PPTP implementations have also suffered from implementation vulnerabilities, such as CVE-2023-28232, which was patched by Microsoft in 2023. However, the fundamental weaknesses of PPTP, MS-CHAPv2, and MPPE are architectural and cannot be fully remediated through patches.

Layer 2 Tunneling Protocol (L2TP) (Do NOT Use)

Refer to https://en.wikipedia.org/wiki/Layer_2_Tunneling_Protocol

  • L2TP is a tunnelling protocol that carries PPP frames over UDP and is most commonly deployed as L2TP/IPsec.

    • L2TP uses UDP port 1701 and provides no encryption, authentication, confidentiality, or integrity protection by itself.
    • L2TP is therefore almost always paired with IPsec, which provides encryption, authentication, and integrity protection.

  • In L2TP/IPsec deployments:

    • IPsec first establishes a secure channel using IKE (typically IKEv1 in traditional Windows L2TP/IPsec deployments).
    • IPsec then protects the L2TP traffic using Encapsulating Security Payload (ESP).
    • User authentication is still performed through the encapsulated PPP session, which may use PAP, CHAP, MS-CHAPv1, MS-CHAPv2, EAP, or certificate-based authentication methods.

  • The cryptographic security of L2TP/IPsec is provided by IPsec rather than L2TP itself.

    • Can be configured using modern IPsec cryptographic suites such as AES, SHA-2, strong Diffie-Hellman groups, and certificate-based authentication
    • Legacy and obsolete cryptographic algorithms, such as DES, 3DES, SHA-1, or weak Diffie-Hellman groups, do not meet modern security requirements.

  • L2TP/IPsec has several operational limitations:

    • It uses double encapsulation (IPsec + L2TP), which increases packet overhead and generally makes it slower than more modern VPN protocols such as IKEv2/IPsec and WireGuard.
    • Traditional IPsec was not designed to traverse Network Address Translation (NAT) devices. NAT Traversal (NAT-T) is therefore required when either endpoint is behind NAT, typically using UDP port 4500.
    • Firewalls must generally permit UDP 500 (IKE), UDP 1701 (L2TP), ESP (IP protocol 50), and often UDP 4500 (NAT-T).

  • L2TP/IPsec has no widely accepted catastrophic protocol break. Most practical security issues arise from legacy cryptographic choices, weak pre-shared keys, or deployment misconfiguration.

    • Deployments that rely on pre-shared keys (PSKs) instead of certificates may be vulnerable to offline attacks if weak shared secrets are used.
    • L2TP itself provides no cryptographic protection. The confidentiality and integrity of the VPN connection depend entirely on IPsec. If IPsec is disabled, omitted, or improperly configured, L2TP traffic is not protected.

  • L2TP/IPsec is generally considered a legacy VPN technology and has largely been superseded by IKEv2/IPsec, SSTP, OpenVPN, and WireGuard for new deployments.

Secure Socket Tunnelling Protocol (SSTP)

Refer to https://en.wikipedia.org/wiki/Secure_Socket_Tunneling_Protocol

  • SSTP is a Microsoft-developed VPN protocol that encapsulates PPP traffic inside an HTTPS connection.

    • SSTP establishes a TCP connection to the VPN server on TCP port 443 and then negotiates a TLS session.
    • After the TLS handshake completes, PPP frames are transported through the encrypted HTTPS tunnel.
    • Because SSTP uses HTTPS over TCP port 443, it can traverse most firewalls, proxy servers, captive portals, and restrictive network environments that commonly block PPTP or L2TP/IPsec traffic.

  • In SSTP deployments:

    • The VPN server is authenticated during the TLS handshake using an X.509 certificate.
    • User authentication is performed through the encapsulated PPP session, which may use PAP, CHAP, MS-CHAPv1, MS-CHAPv2, EAP, or certificate-based authentication methods such as EAP-TLS.
    • SSTP uses cryptographic binding to help prevent certain man-in-the-middle attacks by linking PPP authentication material to the TLS tunnel.

  • The cryptographic security of SSTP is provided by TLS rather than SSTP itself.

    • When configured with modern TLS versions and strong cipher suites, SSTP can provide strong confidentiality, integrity protection, and server authentication.
    • The security of SSTP depends heavily on the security of the TLS implementation, certificate validation, and certificate management processes.
    • Obsolete TLS versions, weak cipher suites, expired certificates, or improperly validated certificates may reduce overall security.

  • SSTP has several operational characteristics:

    • Since SSTP uses TCP port 443, VPN traffic is difficult to distinguish from normal HTTPS traffic and is therefore less likely to be blocked by intermediate networks.
    • SSTP typically works well through NAT devices and does not require special NAT-Traversal mechanisms.
    • SSTP is primarily intended for remote-access VPN scenarios and is generally not used for site-to-site VPN deployments.
    • SSTP uses TCP transport and therefore inherits the performance limitations of TCP-over-TCP tunnelling, which can cause reduced throughput and increased latency on congested or lossy networks.

  • The principal security risks in SSTP deployments are generally related to TLS and certificate management rather than weaknesses in the SSTP protocol itself.

    • A compromised or improperly issued server certificate may enable impersonation attacks.
    • Misconfigured certificate trust chains, expired certificates, or weak TLS configurations can prevent secure authentication of the VPN server.
    • No widely accepted catastrophic protocol break comparable to PPTP/MS-CHAPv2 is known for properly configured SSTP deployments.

  • SSTP remains a secure and commonly deployed VPN protocol in Windows environments. It is particularly useful in networks where VPN traffic must traverse restrictive firewalls or web proxies.

Internet Key Exchange Version 2 (IKEv2)

Refer to https://en.wikipedia.org/wiki/Internet_Key_Exchange#IKEv2

  • IKEv2 is a modern VPN protocol that uses IPsec to provide authentication, encryption, integrity protection, and secure key exchange.

    • IKEv2 uses the Internet Key Exchange Version 2 protocol to negotiate IPsec Security Associations (SAs) and cryptographic parameters between the VPN client and server.

  • In Windows IKEv2/IPsec deployments:

    • IKEv2 first authenticates the VPN server and client and negotiates cryptographic settings.
    • IPsec then protects user traffic using ESP (Encapsulating Security Payload), providing confidentiality, integrity protection, and replay protection.
    • Authentication can be performed using certificates, EAP-based authentication methods, smart cards, or RADIUS-backed authentication systems.

  • The cryptographic security of IKEv2 is provided by IPsec.

    • When configured with modern cryptographic suites such as AES, SHA-256 or stronger integrity algorithms, and strong Diffie-Hellman groups, IKEv2 provides strong security and is generally considered suitable for enterprise deployments.
    • Perfect Forward Secrecy (PFS) can be enabled to ensure compromise of a long-term private key does not expose previously captured VPN sessions.
    • Legacy cryptographic settings such as 3DES, SHA-1, and Diffie-Hellman Group 2 (1024-bit) no longer meet modern security recommendations. Microsoft recommends configuring stronger alternatives.

  • IKEv2 has several operational advantages:

    • It supports MOBIKE (Mobility and Multihoming), allowing VPN connections to survive network changes such as switching between Wi-Fi and cellular networks without reconnecting the VPN session.
    • It has lower protocol overhead than L2TP/IPsec because it does not require double encapsulation.
    • It generally provides better performance and faster connection establishment than SSTP and L2TP/IPsec.
    • It is the preferred protocol for Windows Always On VPN deployments.

  • IKEv2/IPsec requires specific firewall access:

    • UDP port 500 is used for IKE negotiations.
    • UDP port 4500 is used when NAT Traversal (NAT-T) is required.
    • ESP (IP protocol 50) is used to carry protected VPN traffic.

  • The principal security risks in IKEv2 deployments are generally related to configuration rather than protocol design.

    • Deployments using weak cryptographic algorithms, weak pre-shared keys, or poorly managed certificates may be vulnerable to compromise.
    • Failure to validate certificate chains correctly can weaken server authentication and increase impersonation risk.
    • No widely accepted catastrophic protocol break comparable to PPTP/MS-CHAPv2 is known for properly configured IKEv2/IPsec deployments.

  • IKEv2/IPsec is generally considered Microsoft's preferred VPN protocol for modern Windows deployments. It offers strong security, good performance, support for roaming clients, and broad enterprise adoption.

What VPN Protocols to Use for Production

Since Windows Server RRAS supports IKEv2 and SSTP natively, these are typically the preferred VPN protocols for Windows Server deployments. Windows clients also support IKEv2 and SSTP out of the box without requiring third-party VPN software.

WireGuard and OpenVPN require separate software installations and are not built into Microsoft Windows Server or clients. However, both are widely supported across many operating systems and network appliances, and many commercial VPN solutions use these protocols.

WireGuard is one of the most modern and lightweight VPN protocols in widespread use today and is widely regarded as one of the simplest protocols to deploy securely due to its small code base and use of modern cryptographic algorithms.

Protocol Encryption Best For Status Transport
WireGuard ChaCha20-Poly1305 General Purpose VPN deployments Recommended UDP
OpenVPN AES-256-GCM Restrictive networks Recommended UDP or TCP
IKEv2 AES-256 Mobile devices Recommended UDP
SSTP SSL/TLS Windows-centric environments Acceptable TCP

Another consideration is performance over limited bandwidth, packet loss, or high-latency network connections. VPN protocol selection may be influenced by performance requirements, protocol overhead, and the characteristics of the network environment. For example, organizations may choose a more bandwidth-efficient VPN protocol for remote workers using Always On VPN, Voice over IP (VoIP), video conferencing, screen sharing, or other real-time collaboration applications.

TCP-based VPN tunnels are generally less efficient on poor-quality networks than UDP-based VPN tunnels. While TCP introduces slightly more protocol overhead than UDP, the more significant factor is susceptibility to TCP Meltdown (also known as the TCP-over-TCP problem).

TCP Meltdown occurs when a TCP connection is encapsulated inside another TCP connection. Both the inner and outer TCP layers perform retransmissions, congestion control, packet ordering, and flow control. When packet loss, congestion, or high latency occurs, the behaviour of the two TCP layers can interfere with one another, resulting in increased latency, reduced throughput, and potentially severe performance degradation.

In environments with limited bandwidth, packet loss, or high latency, the following ranking is generally appropriate:

  1. WireGuard (Best)

    • Uses UDP and has very little protocol overhead.
    • Does not introduce an additional TCP layer. TCP-based applications continue to use their native congestion-control mechanisms without interference from a second encapsulating TCP session.
    • Widely regarded as one of the fastest modern VPN protocols.

  2. IKEv2/IPsec (Very Good)

    • Uses UDP and therefore avoids TCP Meltdown.
    • Supports MOBIKE, which helps maintain VPN connectivity when a device changes networks.
    • Often the best choice when native Windows support is desired.

  3. OpenVPN ((UDP: Very Good, TCP: Fair)

    • When configured with UDP, it performs similarly to WireGuard and IKEv2.
    • When configured with TCP, it becomes susceptible to TCP-over-TCP (TCP Meltdown) effects.
    • TCP mode is often used because it can traverse restrictive networks that block UDP traffic.

  4. SSTP (Worst under poor network conditions)

    • Encapsulates VPN traffic inside HTTPS over TCP port 443.
    • Extremely firewall-friendly, but can experience TCP Meltdown and significantly reduced throughput on lossy or high-latency links.
    • Best suited for restrictive corporate, hotel, or public networks where other VPN protocols may be blocked.
