06 - Authentication & Policies

Securing modern Windows Server environments requires a thorough understanding of authentication mechanisms, service identities, and account security policies. This content explores the technologies and administrative practices used to manage authentication and authorization in Active Directory, including Kerberos, Service Principal Names (SPNs), service accounts, Managed Service Accounts (MSAs), Group Managed Service Accounts (gMSAs), and the newer Delegated Managed Service Accounts (dMSAs) introduced in Windows Server 2025.

It also examines domain account policies such as password policies, account lockout settings, and fine-grained password policies implemented through Password Settings Objects (PSOs). By understanding and properly configuring these features, administrators can strengthen security, reduce administrative overhead, and ensure that services and users can securely access the resources they require while maintaining compliance with organizational security standards.

AD DS Authentication Protocols

  • Authentication is the act of confirming the identity of a user or system and is an essential part of authorization when the user or system tries to access a server or network resource.
  • Because authentication is such a key component in security, you need to choose the appropriate authentication method.
  • Two primary authentication protocols used in Active Directory environments are NTLM and Kerberos.
  • Modern Active Directory environments should use Kerberos whenever possible. NTLM remains available in AD for backward compatibility but should be minimized/disabled where possible.

NTLM Authentication

NT LAN Manager (NTLM) is a suite of Microsoft security protocols that provides authentication, integrity, and confidentiality for network communications between clients and servers.

  • Protocols: LANMAN + NTLMv1, NTLMv2, NTLM2
  • Successor to LAN Manager (LANMAN)
    • It provides compatibility with older systems and applications

When either a Windows client or Windows server or both are not joined to a domain, or not part of the same trusted domain environment, Windows will use NTLM for authentication. Some old NAS devices and SMB shares may also fall back to NTLM authentication, even if domain authentication is available.

NTLM passwords are considered weak because they can be brute-forced with modern hardware. NTLM does not support modern and secure algorithms; it uses CRC or MD5 hash for integrity, and RC4 for encryption.

For more details and information, refer to Wikipedia Article on NTLM.

Kerberos

Source: https://en.wikipedia.org/wiki/Kerberos_(protocol)

Kerberos is a computer network authentication protocol that allows hosts to prove their identity over an unsecured network in a secure manner.

Kerberos is based on open standards. A free implementation is available from MIT under the BSD license and is written in C. Microsoft and other vendors use their own implementation of the same protocols. The ITFE (Internet Engineering Task Force) describes Kerberos Version 5 specifications under the following standards:

  • Encryption and Checksum Specifications (RFC 3961).
  • Advanced Encryption Standard (AES) Encryption for Kerberos 5 (RFC 3962).
  • The Kerberos Network Authentication Service (V5) (RFC 4120)
  • The Kerberos Version 5 Generic Security Service Application Program Interface (GSS-API) Mechanism: Version 2 (RFC 4121).

Kerberos authentication is available for many platforms such as Unix, Linux, z/OS (IBM Mainframes), macOS (Apple) and even some embedded and IoT devices.

Kerberos is the primary authentication protocol for Microsoft Active Directory environments since Windows 2000. Microsoft has made some changes to their Kerberos implementation, such as additional functionality described in RFC 3244 (Microsoft Windows 2000 Kerberos Change Password and Set Password Protocols) and RFC 4757 (The RC4-HMAC Kerberos Encryption Types Used by Microsoft Windows).

Kerberos relies heavily on accurate time synchronization. If the time difference between a client and a server (such as a domain controller) exceeds the configured tolerance, Kerberos authentication may fail. Therefore, proper time synchronization methods and protocols must be in place for all servers and clients.

  • In Windows environments, domain controllers and member computers should maintain synchronized clocks.
    • By default, Active Directory uses the Windows Time service (W32Time) to maintain time synchronization throughout the domain.
  • Other OS and platforms may use other protocols such as NTP (Network Time Protocol).
  • It is usually beneficial to have time servers on a network, which may have several servers and clients to support various functions, not limited to Kerberos authentication.

Kerberos Operation

Source: https://en.wikipedia.org/wiki/Kerberos_(protocol)#Protocol

Kerberos uses tickets instead of transmitting credentials across the network. It relies on a trusted authentication server and can use a mix of symmetric and optionally asymmetric encryption. It uses port UDP 88 by default. Components of the authentication system are:

  • Key Distribution Center (KDC)
    • Authentication Server (AS)
    • Ticket-Granting Server (TGS)
  • Client
  • Service Server (SS)

All services are registered with the Ticket-Granting Server (TGS) and are given a unique Service Principal Name (SPN).

When the client successfully logs on and authenticates to the Authentication Server (AS), it is granted a Ticket-Granting Ticket (TGT). The TGT includes the Client ID, client network address, ticket validity period, and the Client Ticket-Granting Server (TGS) Session Key.

When the client needs to access a service, the client sends a request to the Ticket-Granting Server (TGS) using the TGS session key provided in the Ticket-Granting Ticket (TGT) and referring to the service using the SPN. If the client is granted access, it is issued a Service Ticket (ST), which is sent to the Service Server (SS) along with its service request by the client.

For a general overview of the Kerberos authentication and authorization process, refer to the Wikipedia Article on Kerberos (protocol) and the section on the Protocol operation.

For reference material on how Kerberos V. 5 works in Windows environments, refer to Microsoft Learn How the Kerberos Version 5 Authentication Protocol Works, and for the contents of tickets, refer to section on What Is in a Ticket? in the same article.

Securing Services

Authentication and authorization can be performed at the service level. Generally, services are required to run under a security principal that can be managed by AD DS. The following are some of the mechanisms by which authentication and authorization processes can operate in a Windows AD environment.

Service Principal Names (SPN) in Windows Domain

Source: https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2003/cc772815(v=ws.10)?redirectedfrom=MSDN#service-principal-names

SPNs are unique identifiers for services running on servers. Every service that uses Kerberos authentication needs to have an SPN set for it so that clients can identify the service on the network. If an SPN is not set for a service, then clients will have no way of locating that service. Without properly set SPNs, Kerberos authentication is not possible.

An SPN typically follows the format serviceclass/hostname[:port]. For example:

  • HTTP/webserver.example.tld.
  • MSSQLSvc/sql01.example.tld:1433

An SPN is registered in Active Directory under a principal (that is being used as the Service Account) as an attribute called Service-Principal-Name. In modern Windows Server environments, those principals commonly include:
- Computer accounts
- Traditional user accounts used as service accounts
- Managed Service Accounts (MSAs)
- Group Managed Service Accounts (gMSAs)
- Delegated Managed Service Accounts (dMSAs) in Windows Server 2025

A Kerberos-enabled service will be running under a principal (Service Account) that has the SPN defined in its attribute. Any service can look up the SPN for another service. When a service wants to authenticate to another service, it uses that service's SPN to differentiate it from all of the other services running on that computer.

As has been discussed in previous topics, if a service account were simply a user account with a human-generated password, then that account would be more vulnerable to an offline dictionary attack. From a security standpoint, setting an SPN on a principal being used as a service account is as important as creating that account.

Delegated Managed Service Accounts (dMSA)

As a review from previous content:

  • Service Accounts were regular user accounts (local, domain, or built-in accounts) that were used to run a service. The credentials for these accounts are created manually. Traditional Service Accounts have several security problems and shortcomings:
    • Passwords are often configured to never expire.
    • Passwords may be shared across multiple servers.
    • Compromised passwords can be used from any machine.
    • Service accounts are common targets for Kerberoasting and other credential theft attacks.
  • A Managed Service Account (MSA) is a special Active Directory account object that provides automatic password management and automatic Service Principal Name (SPN) management for services running on a single server.
  • Group Managed Service Accounts (gMSAs) extend this functionality by allowing multiple authorized servers to run services using the same managed account while Active Directory automatically generates and periodically rotates the account password.

A Delegated Managed Service Account (dMSA) is a new type of managed service account introduced in Windows Server 2025. Its primary purpose is to provide a secure migration path away from traditional service accounts while reducing the risks associated with long-lived passwords and credential theft. Unlike traditional service accounts, dMSAs use managed credentials and tie authentication to authorized machines rather than relying solely on a reusable password.

Windows Server 2025 addresses these issues with dMSAs by:

  • Automatically managing credentials.
  • Binding authentication to specific machine identities (other systems cannot use the same credentials).
  • Preventing direct use of traditional service account passwords (uses "machine-bound ID" and Keys with automatic key rotation).
  • Supporting gradual migration from legacy service accounts to dMSA
    • Can NOT migrate an MSA or a gMSA to dMSA.

Refer to the Microsoft Learn article on Delegated Managed Service Accounts overview for more details, such as limitations and migration.

Kerberos Delegation

Kerberos delegation is a feature of the Kerberos authentication protocol that allows a service to obtain access to another network service on behalf of a user, without requiring the user to re-enter their credentials. It is commonly used in multi-tier applications where one server must access another server while preserving the user's identity (for example, it allows a web server to access a database server using the user's ID instead of its own).

  • Kerberos Delegation can be configured as:
    • Unconstrained Delegation:
      • The service is trusted to delegate user credentials to any service in the domain.
        • Simplest to configure and least secure.
    • Constrained Delegation:
      • The service can delegate credentials only to specific services that an administrator explicitly allows.
        • Reduces the attack surface compared to the unconstrained variant
    • Constrained Delegation with Protocol Transition:
      • Allows a service to accept non-Kerberos authentication, convert to Kerberos, and delegate the user's identity to approved services
      • Used for environments or applications that must support multiple authentication protocols

The general recommendation is to use Kerberos Constrained Delegation (KCD) whenever delegation is required and avoid unconstrained delegation unless necessary.

Virtual Accounts

  • Virtual accounts were introduced in Windows 7 and Windows Server 2008 R2.
  • A virtual account uses the format: NT SERVICE\<ServiceName>.
  • Virtual accounts provide advantages over traditional service accounts by providing accounts that are managed automatically by Windows and do not require administrators to create or maintain passwords.
  • Virtual accounts are limited to individual servers and cannot be shared across multiple systems. Their identity is local to the computer on which they run.

Virtual Accounts use cases are:

  • A service runs on a single server, and you do not need a shared identity across multiple servers.
  • The service only needs local permissions or limited or no domain access.
  • You want a simpler alternative to creating a dedicated service account, and for Windows to automatically manage local service account credentials.

Authentication Policies

In Active Directory environments, account policies are typically configured at the domain level to ensure consistent authentication and security settings across domain users and computers.

  • Group Policies: provide centralized management of user and computer settings.
  • Group Policy Objects (GPOs): are collections of user and computer settings.
  • Account policies define security settings such as:
    • Password policy
    • Fine-Grained Password Policies
    • Account lockout policy
    • Kerberos policy

Most account policies can be configured using Group Policy Management Editor under the Default Domain Policy:

  • Account Policies: Computer Configuration\Windows Settings\Security Settings\Account Policies
  • Account Lockout Policies: Computer Configuration\Policies\Windows Settings\Security Settings\Account Policies\Account Lockout Policy
    • Define Lockout threshold, Lockout duration, and reset account lockout counter
  • Password Policies: Computer Configuration\Policies\Windows Settings\Security Settings\Account Policies\Password Policy
    • Define password requirements, complexity settings, and password lifetimes.
  • Kerberos Policies: Computer Configuration\Policies\Windows Settings\Security Settings\Account Policies\Kerberos Policy
    • Configurations include:
      • Enforce user logon restrictions: Determines whether the Key Distribution Center (KDC) validates user account restrictions, such as logon hours and account restrictions, before issuing service tickets.
      • Maximum lifetime for service ticket
      • Maximum lifetime for user ticket: Specifies how long a Ticket Granting Ticket (TGT) remains valid before the user must obtain a new one.
      • Maximum lifetime for user ticket renewal: Specifies how long a user's Ticket Granting Ticket (TGT) can be renewed without requiring the user to reauthenticate.
      • Maximum tolerance for computer clock synchronization: Specifies the maximum allowed time difference between domain-joined computers and domain controllers before Kerberos authentication fails.
    • The effective Kerberos policy for domain users is determined by the Kerberos Policy settings configured at the domain level.

For Fine-Grained Password Policies, use Password Settings Objects (PSOs) in AD. Then apply them directly to users and security groups. When multiple PSOs apply to a user, the PSO with the lowest precedence value takes priority.

Password Settings Objects can be configured using Active Directory Administrative Center (ADAC):

  • Navigate to: System\Password Settings Container to view or create a new Password Settings Object.
  • Typical configurations:
    • Minimum password length
    • Password complexity requirements
    • Password history
    • Minimum password age
    • Maximum password age
    • Account lockout threshold
    • Account lockout duration
    • Reset account lockout counter after
