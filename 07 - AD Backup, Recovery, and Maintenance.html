07 - AD Backup, Recovery, and Maintenance

When using information technology, information security must be taken into account. Because systems that are designed and built to be maintainable are generally easier to secure, it is important to consider both maintainability and security during the planning and design phases. Attempting to add security and maintainability after a system has been deployed to production is typically more difficult, more costly, and less effective.

Infrastructure Planning and Maintenance

Building With Correct Solutions and Implementation

  • Proper Networking segmentation
  • Load Balancing
  • High Availability

    • Detailed Network Topology

    • Detailed Active Directory forest and domain topology
    • Detailed information of each system
      • DNS servers
      • Domain controllers

Planning for Disaster

You have come across these concepts in your other courses. If you would like a review of the standard DR concepts and Microsoft-specific perspective, you can refer to the Microsoft Learn article on What are business continuity, high availability, and disaster recovery?

  • OR planning is done during the design phase, extended into the implementation phase
  • Must have completed a risk assessment and a business impact analysis to determine how and where to allocate resources
    • Determine acceptable downtime and data loss through Recovery Time Objectives (RTOs) and Recovery Point Objectives (RPOs).

Maintaining and Testing

  • All recovery solutions should be tested periodically to validate that the backups and restore solutions are still working
  • Are the staff able to perform the tasks when the real disaster strikes?
  • Do documentation or procedures need to be updated?
    • What information can potentially be lost, what shortcomings are there
    • New software/OS versions, changes in technologies, changes in usage patterns, changes in costs, etc.
    • Does the current solution still align with business objectives (RPO, RTO), and costs/budgets

Impact of Virtualization and Cloud

For the purposes of this topic, virtualization is defined as software abstraction of the hardware layer, and cloud computing is defined as software abstraction of the virtualization layer that provides on-demand access to computing resources and services over a network, typically through self-service provisioning, automation, elasticity, and consumption-based billing.

  • Using VMs and Containers instead of physical machines:
    • Decouples the system from hardware
    • Efficient use of hardware resources and more optimal/higher utilization
    • Access to backup, replication, cloning, and migration capabilities that are often simpler and more accessible than with bare-metal implementations.
      • Virtual machines can often be backed up at the VM level, simplifying backup and recovery;
      • VMs can be moved from host to host during maintenance or in case of failure, reducing downtime and increasing availability.
      • Please note: Some applications require application-level awareness of VM migration, backup/restore, and VM moves and migrations. Some examples include:
        • Microsoft Active Directory Domain Services, Microsoft SQL Server, Microsoft Exchange
        • In general, clustered, distributed, or sharded systems may require special handling of transaction logs, replication metadata, timestamps, node identities, or quorum information to maintain consistency and synchronization.
    • Virtualization of network infrastructure through virtual switches, virtual routers, VLANs, and software-defined networking (SDN), reducing the amount of physical networking hardware that must be managed directly.
    • Automation possibilities, such as Infrastructure-as-Code

In short, virtualization provides significant operational benefits:

  • Rapid deployment
  • Simplified backup
  • Host migration
  • High availability
  • Disaster recovery

However, virtualization has limitations and challenges and may not always be feasible. Some limitations and challenges may include:

  • Required access to bare-metal hardware, such as GPU Acceleration or hardware security modules, etc.
    • Even if using pass-through technologies, VMs may be bound to physical hosts, limiting benefits
  • May still need some systems installed as bare metal to reduce complexity
    • Example: Virtual NAS and SAN solutions are possible, but they ultimately depend on underlying physical storage infrastructure.
    • Example: Virtual Router or other network device is useful, but also tied to physical network links or hardware
  • Licensing and rights limitations
    • Licensing and use of products in virtualization or cloud environments vary from product to product and vendor to vendor. This includes proprietary OSes (such as Windows Server), and all software installed within
    • For Windows Server 2025 licensing details for DR-related VMs, see Disaster recovery rights
  • Other application or software-specific requirements
    • Cloning virtual machines may require additional steps and may require additional safeguards.

Active Directory Virtualization Considerations and Safeguards

Windows Server AD domain controllers require special consideration when performing some tasks at the VM level, which may lead to replication problems and corruption within the Windows Server environment:

  • VM full backups/restore and VM Snapshot backup/restore operations
  • VM cloning operation
  • VM migration (move to another host)

Microsoft provides detailed considerations and solutions in Microsoft Learn documentation that you should read:

  • Requirements for virtualized DC cloning
  • Safely virtualizing Active Directory Domain Services (AD DS) for topics such as:
  • Effects on Update Sequence Numbers (USNs) and InvocationIDs
  • Virtualization-based safeguards (How AD DS guest uses VM-GenerationID from the hypervisor to detect time-shift events such as backup/restores, snapshot rollbacks, or cloning)
  • How to detect and recover from such issues

What Must Be Protected in AD DS

Active Directory Domain Services (AD DS) is composed of several interconnected services and data stores. Proper backup and recovery planning requires understanding what components are critical to operations. A healthy Active Directory deployment depends on:

  • ntds.dit
  • Transaction logs
  • SYSVOL
  • DNS
  • Group Policy Objects (GPOs)
  • Domain Controller metadata
  • Replication topology

Main Components

  • The Active Directory database: ntds.dit
    • It stores:
      • Users, Groups, Computers, Organizational Units (OUs)
      • Domain configuration information
      • Forest configuration information
      • Schema information
    • The database uses Microsoft's Extensible Storage Engine (ESE/ESENT).
  • SYSVOL
    • Contains:
      • Group Policy files
      • Administrative templates
      • Logon scripts
      • Startup and shutdown scripts
    • All domain controllers maintain a synchronized copy of SYSVOL.
      • Modern Active Directory environments use DFS Replication (DFSR)
      • Legacy environments (older than Server 2016) may still contain references to File Replication Service (FRS)
  • DNS
    • AD is heavily reliant on DNS for supporting:
      • Domain controller location
      • Authentication
      • Replication
      • Group Policy processing
      • Service discovery
    • Loss of DNS can severely affect Active Directory functionality.

Windows Server Backup Tools

Currently, Microsoft supports the following tools for performing backups:

  • Windows Server Backup GUI utility:
    • Install the Windows Server Backup feature using the Add Roles and Features Wizard
      • Refer to Microsoft Documentation for detailed procedures to Install Windows Server Backup
  • Wbadmin.exe CLI utility
  • Enterprise backup solutions:
    • Products and solutions such as Azure Backup, MARS (Microsoft Azure Recovery Services), Azure Backup Server, and associated services, such as REST API access, Identity and secrets management, encryption, etc. for on-prem and cloud.

To access and operate Windows Server Backup and wbadmin, the user accounts that perform configuration tasks (such as installation and scheduling tasks) must be members of the Administrators group; to perform a backup task, they must be a member of the Backup Operators or Administrators group.

Backup Strategies for Windows Server

Backup planning should be performed during the design stage of an Active Directory deployment and should align with organizational RTO and RPO requirements.

System State Backups

A "System State" backup is the minimum backup recommended for protecting a domain controller. A System State backup may include:

  • Active Directory database (ntds.dit)
  • SYSVOL
  • Registry
  • Boot files
  • COM+ configuration
  • Certificate Services data (if installed)

In Server 2025, a system state backup can be performed:

  • Using Windows Server Backup for System State Backup
  • Using Wbadmin.exe for System State Backup

Bare Metal Recovery (BMR)

A Bare Metal Recovery backup is designed to restore an entire server. The backup image can be stored in local disks, external or removable disks and media (tape, DVD, etc), or network storage. Use-cases include:

  • Full operating system recovery (for example, useful in case of OS corruption or storage failure)
  • Hardware replacement scenarios (Restore to different hardware)
  • Disaster recovery planning
  • Recovery of complete domain controllers
  • Organizations should strongly consider BMR backups for critical infrastructure servers.

Refer to Active Directory Forest Recovery - Back up a full server for detailed procedures:

  • Using Windows Server Backup for a full server backup
  • Using wbadmin.exe for a full server backup.

Active Directory Recovery Concepts

Administrators should understand the available recovery methods even if they do not routinely perform them.

Directory Services Restore Mode (DSRM)

DSRM is a special recovery mode used when Active Directory must be recovered or repaired. The system is rebooted specifically into the DSRM mode using:

  • Advanced Startup Options menu via the F8 button during boot, and choosing Directory Services Restore Mode.
    • Requires impeccable timing for hitting the F8 button during boot on modern systems, and fast-boot may prevent this from succeeding
  • Using the System Configuration, msconfig.exe, and selecting Safe boot > Active Directory repair.

This is an offline recovery method. Typical uses include:

  • Forest recovery
  • System State restoration
  • Authoritative restores
  • Certain AD DS maintenance tasks

You are required to have the DSRM credentials as set during the installation and configuration phase of the AD DS role.

Non-Authoritative vs. Authoritative Restore

A non-authoritative restore restores a domain controller from a System State backup. The newer changes to the forest since the state backup was taken are obtained from replication partners.
A typical use case is for recovering or rebuilding a single failed or damaged domain controller, while allowing changes to be replicated back to the restored DC from other healthy domain controllers in the forest.

An authoritative restore restores all objects from backup such that it forces restored objects to overwrite newer replicated versions on other DCs. This means that the restored state will be propagated to other DCs in the forest, overriding their current state. Typical uses include recovering deleted users, groups, and OUs.

AD Object Recovery

Most day-to-day recovery operations involve recovery of deleted objects rather than restoring an entire domain controller from state or full-system backup since they can be cumbersome and time-consuming.

Active Directory Recycle Bin

The Active Directory Recycle Bin is the preferred method for recovering deleted objects since Windows Server 2008 R2. As a best practice:

  • Enable the Active Directory Recycle Bin early in the lifecycle of a new Active Directory environment.
  • Use the Protect object from accidental deletion feature in the Active Directory Administrative Center (ADAC), and Active Directory Users and Computers (usually enabled by default when creating new objects).

Benefits include:

  • Faster recovery and reduced need for authoritative restores
  • Preservation of object attributes (For example, restored user accounts automatically regain all group memberships and corresponding access rights that they had immediately before deletion, within and across domains.)

Legacy Object Recovery Methods Without Using the Recycle Bin

These methods are rarely used in modern environments and primarily exist for compatibility with legacy recovery scenarios. Recycle Bin restoration is the proffered and recommended method since it restores the object and all of its attributes. However, if Recycle Bin is not enabled or not available (such as legacy systems such as Server 2003), Tombstone Reanimation may be an option.

  • When objects are deleted, they are not immediately removed. The objects are simply moved through stages before they are discarded:
    • Live Object → Tombstoned Object → Recycled Object → Permanent Deletion
  • Objects that are "Tomestoned" will lose most of their attributes and will require manual attribute restoration after object restoration
    Tombstone Reanimation can be performed using:
    • The LDP.exe legacy GUI utility (Using the LDAP protocol to connect/bind to AD and searching for deleted objects using CN=Deleted Objects)
    • PowerShell-Based Tombstone Reanimation, which requires building the query to find the object and to provide a restore path
    • Custom C++ code as shown in the example on Microsoft Learn Restoring Deleted Objects

Active Directory Snapshots

Active Directory snapshots provide point-in-time views of the Active Directory database. Snapshots should not be considered a replacement for backups. They are primarily an administrative and troubleshooting tool.

Snapshots are useful for:

  • Auditing
  • Troubleshooting
  • Investigations
  • Viewing historical data

Utilities to perform and view:

  • ntdsutil utility for taking snapshots (legacy tool), used to create and delete database snapshots.
  • dsamain CLI Utility used to mount and unmount database snapshots.

Managing Active Directory Offline

Certain maintenance tasks may require Active Directory services to be stopped temporarily. Examples include:

  • Database integrity verification
  • Offline maintenance
  • Database recovery procedures

Modern versions of Windows Server support Restartable Active Directory Domain Services, which reduces the need to reboot a domain controller for many maintenance operations.

Offline Defragmentation

Offline database defragmentation may be performed when:

  • Large numbers of objects have been removed
  • Database space reclamation is required

However:

  • It is rarely required in well-maintained environments.
  • It is typically performed only under specific operational circumstances.

Metadata Cleanup

When a domain controller is properly retired (DC is demoted), Active Directory metadata is removed automatically during demotion. However, under certain conditions, metadata of a DC may remain in the database. Some examples of these situations include:

  • A domain controller permanently fails (for example, a total hardware failure, or the system is lost or destroyed due to a physical or cyber incident)
  • A server cannot be properly demoted

Metadata clean up can be performed from the Active Directory Users and Computers console, Active Directory Sites and Services utility, or via CLI using ntdsutil. Refer to the Microsoft Learn article on Clean up Active Directory Domain Controller server metadata.

Active Directory Replication

Microsoft recommends that every Active Directory domain environment should have a minimum of two domain controllers to provide redundancy and avoid a single point of failure. All domain controllers in a forest remain in sync and consistent through the replication process. Replication ensures that all domain controllers maintain consistent copies of:

  • Users
  • Groups
  • Computers
  • Group Policies
  • DNS information
  • Configuration information

Intrasite vs Intersite Replication

  • Intrasite replication occurs between domain controllers located in the same Active Directory site.

    • Intrasite replication characteristics include:
      • High-frequency replication
      • Change notification
      • Optimized for high-speed network connections

  • Intersite replication occurs between different Active Directory sites.

    • Intersite replication characteristics include:
      • Scheduled replication
      • WAN optimization
      • Bandwidth control

Replication Monitoring and Troubleshooting

Several tools can be used to monitor and check the status of replication, including:

  • repadmin CLI utility
  • PowerShell Active Directory cmdlets
  • Active Directory Sites and Services
  • Windows Event Viewer

For troubleshooting replication and common errors, refer to Microsoft Learn documents:

  • Repadmin
  • Diagnose Active Directory replication failures
  • Active Directory replication troubleshooting guidance
  • Advanced Active Directory Replication and Topology Management Using Windows PowerShell

Read-Only Domain Controllers (RODCs)

Read-only domain controllers (RODCs) are used in environments where there is a need for a domain controller in a branch office that does not have a secured physical environment such as:

  • Branch offices
  • Temporary facilities
  • Remote locations

RODCs contain:

  • Read-only Active Directory databases
  • Read-only DNS data
  • Limited credential caching

RODCs have specific configurations and policies:

  • Password Replication Policies (PRP) determine:
    • Which credentials may be cached
    • Which credentials may not be cached
    • Which users can authenticate offline
  • Filtered Attribute Sets
    • Sensitive attributes can be configured so that they are not replicated to RODCs, to reduce risk if an RODC is stolen or compromised.

Legacy Topic: SYSVOL Migration from FRS to DFSR

The TLDR:

  • Older Active Directory environments used File Replication Service (FRS) to replicate SYSVOL across Domain Controllers (legacy, cannot be used with current versions)
  • Modern Active Directory environments use Distributed File System Replication (DFSR) for SYSVOL replication (current system, must migrate replication to this before upgrading Windows Server).

Many environments started off as an Active Directory environment running earlier versions of Windows servers such as Windows Server 2003, and upgraded to newer releases over time. The File Replication Service (FRS) was being used for earlier versions of Windows Server; however, Microsoft introduced Distributed File System Replication (DFSR) as the replacement for FRS beginning with Windows Server 2008. Windows Server 2012 would not allow FSR-based servers to be promoted to Domain Controllers, and FSR support for SYSVOL has been removed since Server 2016. If you ever, in an unlikely scenario, run into this, then here is the documentation to Migrate SYSVOL replication from File Replication Service (FRS) to Distributed File System Replication (DFSR).
