03 - Active Directory Domain Service

Source: https://learn.microsoft.com/en-us/shows/introtoad/02

AD DS provides a centralized system for managing users, computers, and other resources on a network. AD DS features include:

  • Centralized directory
  • Single Sign-on (SSO) access
  • Integrated security
  • Scalability
  • Common management interface

AD DS centralizes network management by providing:

  • A single location and set of tools for managing user and group accounts
  • A single location for signing and access to shared network resources
  • Directory services for AD DS-enabled applications
  • Options for configuring security policies that apply to all users and computers, including management of user desktops and security settings (Group Policy)

Communication Protocols

AD DS relies on several protocols for its functions:

  • LDAP/LDAPS for directory access
  • Kerberos for authentication
  • DNS for service location
  • SMB and RPC for various directory functions and replication activities

LDAP(S) is an X.500 standard based on TCP/IP, and is a client-server model for accessing, searching and modifying a directory service. Refer to Wikipedia articles for X.500 and LDAP for more information.

Authentication vs. Authorization

Authentication is the process of verifying the identity of a user or system on a network. Two components of AD DS Authentication are interactive logon (grants access to the local computer) and network authentication (grants access to network resources).
Authorization is the process of verifying that an authenticated user has permission to perform an action. When a user account is created, an SID (Security Identifier) is issued to the user. During the authentication process, security tokens are created that contain the user's SID and all related group SIDs. Shared resources on a network include ACL (Access Control List) that define who can access the resource. Security tokens are compared against the DACL (Discretionary Access Control List) on the resource to grant or deny access.

AD DS Installation Requirements

  1. TCP/IP network and DNS server addresses
  2. Local administrator account credentials for the server if new domain controller, or an account that is a member of the Domain Admin group if installing additional AD DS in an existing domain
  3. Domain Name System (DNS) Infrastructure must be in place. DNS server can be installed along with the AD DS service if needed. If using or updating existing DNS zones, you must have the required credentials and permissions to the parent DNS zone to allow DNS delegations to be created by the installation process.

AD DS DNS Requirements

  1. AD DS requires a DNS infrastructure to function
  2. AD domain names must be DNS domain names (must be FQDN)
  3. AD DS domain controller records must be registered in DNS to enable other domain controllers and client computers to locate the domain controller using FQDN (via srv records)
  4. DNS zones can be stored in AD DS as Active Directory integrated zones (DS can be used to manage, replicate and enforce the security boundary of the DNS zone file)

AD DS Components

Physical components:

  • Data store (required component)
  • Domain controllers (required component)
  • Global Catalog server (At least one is required)
  • Read-Only Domain Controller (RODC) (optional component)

Logical Components:

  • partitions
  • schema
  • domains
  • domain trees
  • forests
  • sites
  • organizational units (OUs)

AD DS Physical Components

Domain Controllers

A domain controller is a server with the AD DS server role installed and has been specifically promoted to a domain controller.

  • Host a copy of the AD DS directory store
  • Provide authentication and authorization services
  • Replicate updates to other domain controllers in the domain and forest
  • Allows administrative access to manage user accounts and network resources

Global Catalog Servers

Global Catalog servers are domain controllers that store a copy of the global Catalog. A global Catalog:

  • Contains a copy of all AD DS objects in a forest that includes a subset of the attributes for each object
  • Improves efficiency of object searches by avoiding unnecessary referrals to domain controllers
  • is typically required for forest-wide logon processes, universal group membership evaluation, and UPN (User Principal Name) resolution.

For basic information, refer to Microsoft Learn article Domain Controller Roles - Global Catalog Server (Since Windows Server 2003)

Microsoft recommendations on Planning Global Catalog Server Placement:

  • Single-domain forest: All domain controllers are configured as Global Catalog servers because there is little additional overhead and it simplifies administration
  • Multi-domain forests: consider authentication requirements, WAN bandwidth, and site topology such as:
    • Network Bandwidth: "place a global catalog at a location that is visited by a large number of roaming users."
    • Application requirements (for example Microsoft Exchange requires low-latency queries for better performance)
    • Providing services to large number of users: "Place global catalog servers at all locations that contain more than 100 users to reduce congestion of network WAN links and to prevent productivity loss in case of WAN link failure."
    • Network Distance from the AD Controllers: "Ensure that the global catalog servers aren't more than one replication hop from the domain controller on which universal group membership caching is enabled so that universal group information in the cache can be refreshed."

The AD DS Data Store

The data store contains the database files and processes that store and manage directory information for users, services, and applications.

  • Consists of a single file Ntds.dit that, by default, is stored at %SystemRoot%\NTDS on all domain controllers (the location is configurable)
  • The file is only accessible through the domain controller processes and protocols

The AD DS Sites, Replication, and Operation Masters

Since AD DS is meant to be scalable, the infrastructure can span multiple networks (sites), sub-domains (trees), and other domains (forests). That means the infrastructure may have multiple domain controllers depending on the scale. The AD DS database needs to stay synchronized across all domain controllers in order to the system to function correctly.

Replication distributes directory updates to the appropriate domain controllers according to the partition being replicate. It ensures all domain controllers have the same information. Replication uses a multi-master replication model and can be managed by creating AD DS sites. The AD DS replication topology is created automatically as new domain controllers are added to the domain; however, it can be modified using sites configuration.

An AD DS site represents a network segment where all domain controllers are connected by a reliable network connection (well-connected IP subnets). Sites depend on network bandwidth. This is usually associated with IP subnets. The site is used as a unit to manage replication and client logon traffic, and are also utilized by site-aware applications such as DFS (Distributed File System) and Exchange Server. Sites can potentially be used to assign group policy objects to span specific users and computers within the site. Sites are not organizational boundaries, meaning an organizational unit can span multiple sites.

In order to prevent conflicting information in the AD DS database during some replication process in a multi-master system, "Flexible Single Master Operations" (FSMO) or "Operations Master" roles are assigned to each domain controller. Operations Master (FSMO) prevent conflicting updates from being made to the database by only allowing specific tasks that no other domain controllers are permitted to perform. Operations Master (FSMO) roles are broken down to 5 separate roles.

The following Operations Master (FSMO) roles perform operations that must occur on only one domain controller in the forest:

  • Schema master
  • Domain naming master

The following Operations Master (FSMO) perform operations that must occur on only one domain controller in a domain:

  • Primary Domain Controller (PDC) emulator
  • Infrastructure master
  • Relative ID (RID) master
Operations Master Role Description Impacts of Failure or Loss
Schema master - Updates and modifications to schema
- One per Forest		 - Failure does not impact users
- Unable to install any applications that modify schema (such as Exchange)
Domain Naming Master - Controls addition or removal of domains in the forest
- One per forest		 - Loss does not affect users
- Unable to add or remove domains from forest
Primary Domain Controller (PDC) Emulator - Originally meant for backward compatibility with NT 4.0, acted as a domain master browser to provides list of domains and workgroups when browser (legacy)
- Coordinates password changes, account lockouts, and time synchronization
- Manages edits to Group Policy Objects (GPO)
- Password changes are sent to PDC Emulator, which updates the global catalog server and provides replication to other domain controllers
- One per domain		 - Loss affects users
- Most heavily used due to tasks it performs
- Time clock drift due to lack of synchronization will cause cascading issues, such as Kerberos authentication failures
- Account lockouts may not work due to the degradation
Infrastructure master - Maintains references to objects located in other domains
- Updates cross-domain references when objects are renamed or moved
- Example: when renaming or moving a member of a group, Infrastructure master updates the groups so they know the new name and location of the member
- One per domain		 - Loss may not be noticed by users
- Loss impacts recently renamed or moved large numbers of objects
Relative ID (RID) master - Assigns unique security IDs (SID) to newly created objects
- Assigns relative identifiers to domain controllers
- Pre-assigns a block of relative IDs to each domain controller for creation of new security principals
- Domain controllers contact RID master when 50% of the supply is used to get more IDs
- One per domain		 - Loss does not affect users
- Admins will face issues when creating objects, or if the domain runs out of Relative IDs to assign
- Will not be able to move objects between domains

AD DS Logical Components

AD DS Schema

The schema defines every type of object that can be stored in a directory, and enforces rules regarding object creation and configuration. For example, Class dictates what objects can be created in the directory, such as an object of class user or an object of class computer. The Attribute dictates what information can be attached to each object, such as display name. A typical object in the Microsoft AD DS schema can have hundreds of attributes, which can be Windows OS or Microsoft-specific.

Domains

Domains are used to group and manage objects in an organization. Installing the domain controller role on a server creates a domain. That domain can be part of a domain tree, and the domain tree can be part of a forest.

  • Domains define an administrative boundary for applying policies to groups of objects.
  • Domains provide a replication boundary for replicating data between domain controllers.
  • Domains provide administrative and replication boundaries, while the forest is generally considered the primary security boundary.

Domain Trees

A domain tree is a hierarchy of domains in AD DS. It consists of a parent domain and sub-domains (child domains). By default, all sub-domains create a transitive two-way trust with other domains and sub-domains in the tree.

Domain Forests

Forests are a collection of one or more domain trees. Forests share a common schema, configuration partition, and a global Catalog to enable search. The global Catalog in a forest contains all the objects in all domains along with a subset of their attributes. This enables searching for objects in all domains in the forest.
The trust is automatically enabled between all domains in the forest. Enterprise Admins and Schema Admins are shared across the entire forest, meaning the same accounts can make changes to all domains in the forest. Domain Admins are limited to a single domain.

Organizational Units (OU)

OUs are AD containers that can contain users, groups, computers, and other OUs. They are used to represent organizational hierarchy and/or administrative logical boundaries within a domain. This enables the objects within an OU to be managed consistently, and allows delegation of administrative privileges and application of policies along OUs as a logical partition within a domain.

The obvious typical use case for an OU is an organization that has multiple departments, and each department manages its own IT. OU allows each departmental IT to manage their own OU. Another example is to have different groups of users within an organization that need special access or specific security configuration requirements that should not be applied to other users and groups. Placing all those users in an OU allows applying different configuration or privileges to their objects (users, computers, groups, etc.) while not affecting others.

Partitions

Also known as naming contexts, are logical, contiguous subtrees of the directory database that define specific scopes of replication and data organization. Instead of replicating the entire database to every domain controller, AD DS divides data into distinct partitions so that each controller only holds the information necessary for its role, optimizing network traffic and administration.
For more information see Microsoft Learn Naming Contexts and Directory Partitions.

Trust

Trust provides a mechanism for users to gain access to resources in another domain. Trust is typically directional and flows from "trusting" to "trusted". The "trusting" domain contains the resources, and allows the "trusted" domains to access those resources. The terms "one-way" or "two-way" are used to indicate the direction of trust.

Additional terminology:

  • Directional Trust: The trust direction flows from the trusting domain to the trusted domain. This type can be one-way or two-way.
    • Domain A trusts domain B; therefore, members of domain B can access resources in domain A.
  • Transitive Trust: Trust is extended beyond another domain to include all the domains trusted by the other domain. Trust flows (transits) through to other domains.
    • Domain A trusts domain B, and domain B trusts domain C; therefore domain A trusts domain C.

In Windows, by default, all domains within a forest automatically trust all other domains in that forest via two-way transitive trust. Trusts can also be extended outside the forest to other domains and can be established manually.

AD DS Objects

The following is a small subset of available objects in AD DS:

  • User: enables network resource access for a user
  • InetOrgPerson: similar to user, but used for compatibility with other directory services
  • Contacts: used to assign email addresses to external users, and does not enable network access.
  • Groups: used to simplify administration of access
  • Computers: enables authentication and auditing of computer access to resources
  • Printers: used to simplify the process of locating and connecting to printers
  • Shared folders: enables users to search for shared folders
