08 - Operations of Complex AD Environments

Many organizations can operate with a single-domain forest. However, larger enterprises may require multiple domains or multiple forests for administrative, legal, security, or organizational reasons. Trust relationships allow users in one domain to access resources located in another domain or forest. Multiple domains or forests should only be deployed when justified by business or security requirements.

AD features that allow large organizations to implement complex environments:

  • Large numbers of objects
  • Organizational Units (OUs)
  • Fine-grained password policies
  • Account lockout policies
  • Multiple geographic locations through Sites, Subnets, and controlling Inter-Site Transport properties for optimizing performance

For large organizations, there are several approaches to implementing security boundaries using complex AD trees and forests. Some examples are:

  • Organizational forest model: Centralizing user accounts, groups, and resources within a single forest for unified management and streamlined administration.
  • Resource forest model: Isolating network resources such as servers, printers, and applications into dedicated forests to simplify management and enhance security.
  • Restricted access forest model: Enforcing strict security boundaries by creating multiple forests without trust relationships, limiting access to sensitive data and resources.

Creating a Child Domain (Creating a Tree)

The prerequisites are a dedicated server with a unique name and a static IP address. On the new server, simply:

  1. Install the Active Directory Domain Services (AD DS) role on a Windows Server.
  2. Select Promote this server to a domain controller.
  3. Choose Add a new domain to an existing forest.
  4. Select Child Domain.
  5. Specify:
    • Parent domain
    • New child domain name (effectively a sub-domain)
  6. Provide Enterprise Admin or Domain Admin credentials.
  7. Configure DNS and Directory Services Restore Mode (DSRM) password.
  8. Step through the rest of the wizard and complete the installation.

Multi-Forest Environments

Multi-forest deployments are commonly used when organizations require strong security boundaries or independent administration. A typical example of multi-forest environments is government contractors that require security isolation.

Multiple forests provide:

  • Separate schema
  • Separate configurations
  • Separate global catalogs
  • Administrative isolation
  • Security isolation

This provides an environment where it is possible for administrators to retain control over their own trees and forests. Trust relationships (Directional and Transitive) are used to allow or deny access to resources to users from other forests.

Domain and Forest Functional Levels (FFLs)

Source: https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/active-directory-functional-levels

Forest Functional Levels (FFLs) define the set of forest-wide Active Directory features that are available and determine the minimum Windows Server version allowed for domain controllers throughout the forest. They affect only domain controllers and AD DS functionality, not client operating systems or member servers.

When deploying AD, you are required to set the domain and forest functional level. If you are deploying a new system, chances are you are using consistent versions of Windows Server (hopefully the latest version). However, when operating within an existing AD environment with multiple domains, trees, and forests, there may be times when the version of the Windows Server installed on various domain controllers is not the same. For example, you may be deploying a new server within an existing domain using Server 2025, while other domain controllers may still be running Server 2022.

An FFL usually contains all the functionality and features of the previous FFLs plus additional functionality and features. If any domain controllers in a domain are running older releases of Windows Server, then the functional level of the domain cannot be raised beyond what that server supports.

Microsoft did not create separate new functional levels for Windows Server 2019 or Windows Server 2022. Those releases continued to use the Windows Server 2016 functional level. Windows Server 2025 introduces the first new functional level since Server 2016. For Windows Server 2025, the minimum functional level for the domain and forest is Windows Server 2016.

The following are some of the FFL features based on the Windows Server version, according to Microsoft Learn Active Directory Domain Services functional levels:

  • Windows Server 2025:
    • Database 32k pages optional feature (see Database 32k pages for Active Directory).
  • Windows Server 2016:
    • Privileged access management (PAM) using Microsoft Identity Manager (MIM)
    • DCs can support automatic rolling of the New Technology LAN Manager (NTLM) and other password-based secrets on a user account configured to require public key infrastructure (PKI) authentication. This configuration is also known as Smart card required for interactive logon.
    • DCs can support allowing network NTLM when a user is restricted to specific domain-joined devices.
    • Kerberos clients successfully authenticating with the PKInit Freshness Extension get the fresh public key identity security identifier (SID).
  • Windows Server 2012 R2:
    • DC-side protections for Protected Users. When Protected Users authenticate to a Windows Server 2012 R2 domain, they're no longer able to:
      • Authenticate with NTLM authentication.
      • Use DES or RC4 cipher suites in Kerberos preauthentication.
      • Be delegated with unconstrained or constrained delegation.
      • Renew user tickets (TGTs) beyond the initial four-hour lifetime.
    • Authentication policies
      • New forest-based authentication policies can be applied to accounts. The policies can control which hosts an account can sign on from, and apply access control conditions for authentication to services running as an account.
    • Authentication policy silos
      • A new forest-based Active Directory object to be used to classify accounts for authentication policies or for authentication isolation. The new object can create a relationship between user, managed service, and computer accounts.

Microsoft recommends that when you deploy AD DS, set the domain and forest functional levels to the highest value that your environment can support to use as many AD DS features as possible. When you deploy a new forest, you need to set both the forest and domain FFLs.

Raising the FFL for a domain and forest has the following requirements (see Microsoft Learn Understanding Active Directory Domain Services (AD DS) Functional Levels)

  • Raise the functional level of a domain or forest only if ALL domain controllers in the domain or forest run the versions of Windows Server that the new functional level supports.
  • You must be a member of the Domain Admins group to raise the domain functional level.
  • You must be a member of the Enterprise Admins group to raise the forest functional level.
  • You can set a domain functional level higher than the forest functional level.
  • You cannot set a domain functional level lower than the forest functional level.
  • Raise the domain functional level on the primary domain controller (PDC) emulator operations master only.
  • Raise the forest functional level on the schema operations master only.
  • After the domain or forest functional level is raised, it cannot be rolled back. However there are specific exceptions that may allow the rollback via PowerShell using Set-ADDomainMode and Set-ADForestMode in certain situations.

To raise the Domain or Forest Functional Level, refer to Microsoft Learn Identifying your functional level upgrade. The following is a simplified overview of the process after you have validated the domain and forest meet the upgrade requirements, and you have identified the specific Operations Master servers to perform the upgrade from:

  1. In Server Manager, open Tools > Active Directory Domains and Trusts.
  2. Right-click Active Directory Domain and Trusts for the forest, or the domain for the domain.
  3. Select Raise Forest Functional Level or Raise Domain Functional Level and follow the prompts.

Trusts

Trusts require reliable name resolution via DNS so that systems can contact the domain. The recommended DNS configurations for appropriate DNS resolution to allow trust in multi-domain or forest systems to function are:

  • Conditional forwarders
  • Secondary zones
  • Stub zones
  • DNS forwarding

We have already covered the basic terminology of trust relationships in AD. Here is a quick overview of the terminology:

  • Directional Trust: The trust direction flows from the trusting domain to the trusted domain.
    • Can be one-way or two-way.
    • Domain A trusts domain B; therefore, members of domain B can access resources in domain A.
  • Transitive Trust: Trust is extended beyond another domain to include all the domains trusted by the other domain. Trust flows (transits) through to other domains.
    • Domain A trusts domain B, and domain B trusts domain C; therefore, domain A trusts domain C.
  • Non-transitive Trust: Authentication is limited strictly to the two domains participating in the trust.

Trust Types

  • Automatic Trust relationships: Two-way transitive trust relationships are automatically created between all domains within a forest.
  • Manual Trust relationships: Trust relationships can be created and managed manually to allow authentication and resource access between domains, forests, and Non-Microsoft Kerberos realms.
    • External Trust: Created manually as a one-way, two-way and usually non-transitive trust between domains in separate forests.
    • Shortcut Trust: Are manually created transitive trusts between two domains in the same forest to provide a shorter authentication path and improve logon and resource-access performance.
      • It can be one-way or two-way.
      • Only needed in large forests, for example to avoid or reduce AD traffic over WAN when users access resources in distant domains.
    • Realm Trusts: Realm trusts connect AD domains to Non-Microsoft Kerberos Version 5 realms, and can be one-way or two-way, transitive or nontransitive.

Trust Operations

Trusts can be viewed, created and managed via the Active Directory Domains and Trusts or via PowerShell:

  • Example, to create a new trust: In Server Manager, open Tools > Active Directory Domains and Trusts, Right-click the domain and choose Properties, select the Trusts tab, click on New Trust..., and follow the prompts in the wizard.
  • Example of PowerShell: netdom trust domain1.com /Domain:domain2.com /add

Trusts can be validated during troubleshooting and after configuration changes. Using Active Directory Domains and Trusts, right-click on the domain and select Properties, navigate to the Trusts tab, select the trust, click on Properties..., and then Validate.

PowerShell Example:

netdom trust adatum.com /Domain:contoso.com /verify
netdom trust adatum.com /Domain:contoso.com /verify

Trust Authentication Scopes

Trust authentication defines how broadly users from a trusted domain can access resources. Authentication Scopes are:

  • Selective Authentication: Only explicitly authorized users may authenticate to specific resources.
    • Recommended for security-sensitive environments.
  • Domain-Wide Authentication: Allows users from a trusted domain to authenticate throughout the trusting domain.
  • Forest-Wide Authentication: Allows users from a trusted forest to authenticate throughout the trusting forest.

Sites, Subnets, and Inter-Site Transports

In previous topics, an AD DS site represents a network segment where all domain controllers are connected by a reliable network connection (well-connected IP subnets). Sites depend on network bandwidth and are usually associated with IP subnets. Sites and subnets represent the physical topology of Active Directory. Benefits of using Sites include:

  • Optimized authentication
  • Improved replication efficiency
  • Reduced WAN utilization
  • Better service location by clients

Subnets map IP networks to Active Directory Sites. The benefits include:

  • Proper domain controller selection
  • Faster logons
  • Improved resource access

Site Links control Inter-Site replication. Administrators can configure the cost, replication schedule, and replication frequency between sites. Lower-cost links are preferred by Active Directory replication.

A new forest initially contains the default site Default-First-Site-Name. All domain controllers are initially assigned there until a site topology is configured. To view, create or manage new Sites or Subnets:

  1. In Server Manager, open Tools > Active Directory Sites and Services.
  2. Expand Sites to view existing sites; right-click Sites to create new sites.
  3. Right-click on Subnets to add new subnets or expand to view existing ones
  4. The Site Links can be viewed and created by navigating to Inter-Site Transports and choosing IP.
    • Costs, replication interval, and schedule can be configured for each site-link under its properties

Managing SRV Records in DNS

SRV (Service Locator) records are special DNS records that allow clients and domain controllers to locate important Active Directory services such as Domain Controllers (LDAP services), Kerberos authentication services, and Global Catalog servers. When a domain controller starts, the Netlogon service automatically registers the appropriate SRV records in DNS.

Active Directory also registers site-specific SRV records based on the domain controller's site membership. These records enable clients to locate and authenticate with domain controllers in their local site whenever possible, reducing WAN traffic and improving logon performance.

Although domain controllers register these records automatically, administrators must ensure they remain accurate and healthy. SRV records should be validated during troubleshooting and after Active Directory infrastructure changes to ensure:

  • Clients can locate the appropriate domain controllers and authentication services.
  • Site-aware clients are directed to domain controllers in the correct Active Directory site.
  • Domain controllers can locate replication partners and Global Catalog servers.
  • Stale records are removed after domain controllers are moved between sites, renamed, demoted, or decommissioned.
  • Authentication, Group Policy processing, and Active Directory replication continue to function correctly.
