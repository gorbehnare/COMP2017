10 - Access Control

Access Control Overview

Source: https://learn.microsoft.com/en-us/windows/security/identity-protection/access-control/access-control

Access Control Lists (ACLs) and System Access Control Lists (SACLs) are supported on Windows Pro, Enterprise, Education, and Pro Education/SE editions. The Windows operating system controls the use of system and network resources through the interrelated mechanisms of authentication and authorization:

  • Authentication: Verifies who the user is.
  • Authorization: Determines what the authenticated user is allowed to access.

After a user is authenticated, Windows uses built-in authorization and access control processes to determine whether the user has the necessary permissions to access a resource.

Security Principals and SIDs

Objects have an owner, but access can be granted or denied to other users and groups to protect the resource from unauthorized use. In Microsoft's access control model, security principals are represented by unique security identifiers (SIDs). Windows does not use usernames when making access decisions; it uses the SIDs instead:

  • SIDs are unique
  • SIDs do not change for the lifetime of the security principal
  • Therefore, SIDs are used internally in permissions and access tokens.

Security principals include:

  • Users
  • Groups
  • Computers
  • Other SID-enabled security principals

An owner is assigned to an object when that object is created. By default, the owner is the creator of the object. No matter what permissions are set on an object, the owner can always change the permissions. Security principals are assigned rights and permissions on objects that inform the operating system what each of them can do.

Containers and Inheritance

A container is an object (such as a folder) that can hold other objects (such as subfolders and files). In a hierarchy of objects, the relationship between a container and its contents is expressed using parent and child terminology. Child objects inherit access control settings from their parent. The inheritance feature causes objects within a container to automatically inherit inheritable permissions from that container, reducing the administrative effort required to manage permissions on individual objects.

Permissions

Permissions are properties assigned to securable objects that control what actions security principals can perform.

  • Windows access control permissions can be applied to securable objects such as files and folders, AD DS objects, registry objects, and system objects such as processes.

    • Permissions for each object type are stored in that object's security descriptor.
    • Permissions can be granted to security principals from the local domain or from trusted domains.

  • NTFS permissions apply to files and folders on NTFS volumes.

    • Stored in the security descriptors of files and folders on NTFS volumes.
    • NTFS permissions apply regardless of whether access is local or through the network.
    • Common NTFS permissions include Read, Write, Read & Execute, Modify, Full Control, List Folder Contents (folders only), and advanced/special permissions.
    • NTFS permissions are inherited by child objects by default.

  • Share permissions apply only on SMB shared resources.

    • Share permissions are evaluated only when resources are accessed over the network through SMB.
    • Actions are Read, Change, and Full Control.
    • Share permissions do not use NTFS-style inheritance because they are assigned at the share level.

In order for users or groups to be able to take action on a shared resource, both the share permissions and the NTFS permissions must grant access. Explicit deny permissions generally override allow permissions during access checks. Local access is granted by evaluating NTFS permissions, while network access evaluates both the share permissions and the NTFS permissions. Effective access for an SMB share accessed over the network will be the more restrictive of the two.

User Rights

User rights grant specific privileges and sign-in rights to users and groups. User rights are assigned to user accounts and groups, whereas permissions are assigned to securable objects. For a list of user rights and more information, refer to the Microsoft Learn article on User Rights Assignment.

Some examples of user rights include:

  • Log on locally
  • Back up files
  • Restore files
  • Shut down a computer
  • Change system time

Security Descriptors and ACLs

A security descriptor (source) is a data structure that's associated with each securable object. All objects in Active Directory and all securable objects on a local computer or on the network have security descriptors to help control access to the objects.

Security descriptors include information about the owner, security principals, and their permissions. Security descriptors contain the access control list (ACL) of an object, which includes all the security permissions that apply to that object. An object's security descriptor can contain two types of ACLs:

  • A discretionary access control list (DACL), which identifies the users and groups that are allowed or denied access.
  • A system access control list (SACL), which controls how access is audited.

This access control model can be used to secure and control access to objects and attributes individually with granular controls over:

  • Files and folders
  • Active Directory objects
  • Registry keys
  • Printers
  • Devices
  • Services
  • Processes and Threads

The benefits of such individual control include:

  • Fine-grained security
  • Delegation of administrative control
  • Custom security designs
  • Protection of organizational resources based on specific organizational needs

Authorization and Access Control Process

Source: https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-principals

The subject is a process initiated by a user or system, and the object is the resource being accessed. When a subject attempts to access an object, the information in the user's access token is compared with the access control entries (ACEs) in the object's security descriptor. For example, the SIDs of security principals contained in the user's access token are compared with the SIDs referenced in the ACEs of the object's security descriptor to determine whether access should be allowed or denied.

Security Context in Authentication

Source: https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-principals#security-context-in-authentication
In Windows, any user, service, group, or computer that can initiate action is considered a security principal. Each security principal (user, group, computer, etc.) has a security context that defines:

  • Identity
  • Group memberships
  • Privileges
  • Permissions
  • Capabilities

Security principals have accounts, which can be local to a computer or domain-based. For example, domain-joined Windows client computers can participate in a network domain by communicating with a domain controller, even when no user is signed in.

To initiate communications, the computer must have an active account in the domain. Before accepting communications from the computer, the Local Security Authority on the domain controller authenticates the computer's identity, and then defines the computer's security context. The same process is applied to define a security context for users or any other security principal after authentication.

This security context defines the identity and capabilities of a user or service on a particular computer, or of a user, service, group, or computer on a network. For example, it defines the resources (such as a file share or printer) that can be accessed and the actions (such as Read, Write, or Modify) that can be performed by a user, service, or computer on that resource.

The security context of a user or computer can vary:

  • From one computer to another, such as when a user authenticates to a server, their primary workstation, or a workstation other than the user's primary workstation.
  • From one session to another, such as when an administrator modifies the user's rights and permissions.
  • The security context is different when a user or computer is operating on a standalone basis, in a mixed network domain, or as part of an Active Directory domain.

Security Groups

Source: https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/understand-security-principals#security-groups

A security group is a collection of user accounts, computer accounts, and other groups of accounts that can be managed as a single unit from a security perspective. In short, a security group is a collection of:

  • Users
  • Computers
  • Other groups

In Windows operating systems, there are several built-in security groups that are preconfigured with the appropriate rights and permissions. Refer to Microsoft Documentation for a list of Default Active Directory security groups for performing specific tasks. Additional custom security groups can also be created by system admins.

Benefits of using security groups include:

  • Simplifying administration by assigning permissions to a security group instead of individual groups or users.
  • Implementing RBAC (role-based access control), for example, assigning permissions based on job roles and functions
  • Security groups also have scopes: local, global, domain local, and universal.
  • Smaller ACLs for improving performance because fewer ACEs must be evaluated.
  • This is effective when there are thousands of users and groups

Groups can be Active Directory-based or local to a particular computer:

  • Active Directory security groups are used to manage rights and permissions to domain resources.
  • Local groups exist in the SAM database on local computers (on all Windows-based computers) except domain controllers. Use local groups to manage rights and permissions only to resources on the local computer.

For descriptions and settings information about the domain security groups that are defined in Active Directory, see Active Directory security groups.

For descriptions and settings information about special identities, see Special identity groups.

Accessing and Addressing Shared Resources

Access to shared resources is typically provided using the UNC (Universal Naming Convention) format: \\servername\share.

UNC paths to shared folders can be mapped to a drive letter on Windows clients for easier access through File Explorer and to improve compatibility with applications that expect drive-letter-based paths.
